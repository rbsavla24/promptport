  - **Radix interaction fixes (2026-10-31, live-verified on a QA bot):** three live defects all traced to the same two causes — React/Radix controls ignore a synthetic `.click()`, and `Escape` is destructive.
    - *Phase + sub-tab routing.* Phase tabs (Pre Call / On call / Post Call) and the "+ API" sub-tabs (Headers / Path / Query / Body / Response / Settings) are Radix triggers that switch on the pointer sequence, not `.click()`. Rows were therefore all landing in the default Headers panel, and a pre-call tool was being written into On Call. Tab selection now escalates to a full pointer sequence and is confirmed via `aria-selected` before the panel is trusted; the panel itself is resolved through `aria-controls` (with the modal open the document holds nine tabpanels, so "last visible tabpanel" picked the wrong one).
    - *Split parameter rows.* A duplicate dispatch in the row-type menu inserted two rows per item, so the Key landed in one row and the variable in the next and the API could not be saved. The option is now dispatched once, the new row is identified by **diffing** the panel's inputs rather than counting from the end (Body owns a pre-existing "Content type" input, and a Variable Row contributes two inputs), and the picker is scoped to that row.
    - *Event subscriptions.* The events menu stays open across option clicks and the trigger **toggles** it, so re-opening per item was closing it on every other press — only part of the selection landed. Worse, the menu was being closed with `Escape`, which bubbles to the surrounding Radix layer: on the Create Subscription dialog that dismissed the whole dialog so **Create was never pressed**, and in the inline "+ API" editor it removed the editor outright, discarding the tool in progress and silently failing every row after it. The menu is now opened once and every option clicked in sequence, and menus are dismissed with a new `dismissMenu()` — a pointerdown on a neutral node inside the host, which the menu reads as "outside" (and closes) while the host reads it as "inside" (and survives). `Escape` is no longer used anywhere in the import path.
    - *Tool identity.* The 2-field dashboard renders tool names only in `aria-label` ("Edit API `<name>`" / "Delete API `<name>`"), never as visible text, and the existence check was scanning the whole document rather than the selected phase panel — so every tool read as "not present" and was created again on each pass. Existence is now checked by `aria-label` within the selected phase panel, which also makes re-runs idempotent.
    - Verified live end-to-end afterwards: one webhook carrying all three events, and both on-call APIs created exactly once with `Authorization` paired in a single Headers row and `client_loan_id` ↔ `custom_args.client_loan_id` paired in a single Body row.

    - *Top-level tab navigation never verified.* `gotoTab()` fired a bare `.click()` on the agent's Radix tab triggers and then waited on a condition written `... || true`, so it reported success unconditionally without ever checking that the tab had switched. A section could run against whatever tab happened to be showing — or find no fields at all and report every item missing. It now escalates to the pointer sequence and confirms `aria-selected`, and each caller fails loudly ("the 'X' tab could not be selected") instead of writing nowhere.
    - *Custom Analysis: the key Type was never selected* (reported by Raj). The Type control is a Radix combobox rendered as `div[role="button"][aria-expanded]`, not an `<input>` carrying its value, and it starts **empty** — the word "Type" on screen is a floating label, not a selection. The finder looked for an input whose value was already a type name, found nothing, and the "it's already String" path set nothing; **Add** stays inert until a type is chosen, so no key was ever created. The trigger is now located within the key row and the type is **always** chosen explicitly, never assumed.
    - *Verification read a list that lags its own backend.* The 2-field dashboard commits a key server-side before the rendered list catches up, so verifying against the fresh DOM reported keys "missing" that were in fact present — which also drove the retry loop to re-add them.
